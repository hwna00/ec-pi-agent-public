# ValueP 이관 검증

## 적용 범위와 출처

이 스킬은 ValueP 이관의 기능 및 회귀 검증에 사용한다. 일반 서버 테스트에는 검증반의 기본 지침을 적용한다.

기준 자료는 사용자가 제공한 `hub:2197`, '[5.6][이카운트 메타] ValueP 이관 테스트 코드 작성 가이드'다.

- 작성일: 2026-09-17.
- 작업: `A26_04411`.
- 게시글에 명시된 stage 커밋: `ce256dd33da6`.

게시글은 당시의 참고 자료다. 현재 소스와 테스트를 확인하고 적용한다. 게시글의 예외나 성공 사례를 모든 이관 작업의 사실로 확대하지 않는다.

## 역할과 권한

- 변경 코드와 테스트를 읽고 실행 근거를 검토한다. 소스, 설정, 테스트를 수정하지 않는다.
- 필요한 테스트의 대상 파일, 좌표, 입력, 기대 결과를 지휘관에게 전달한다. 테스트 작성은 개발반에 맡긴다.
- 코드 탐색은 graphify MCP를 우선 사용한다. 도구가 없으면 지휘관에게 탐색을 요청한다. 호출 실패 시 프로젝트 지침의 폴백을 적용한다.
- DB 조회는 데이터 조사반에, 화면 확인은 현장 조사반에 요청한다. 요청은 지휘관을 통해 전달한다.
- 이 스킬은 도구나 쓰기 권한을 추가하지 않는다. 테스트 실행 전 빌드, 배포, DB fixture, 산출물 쓰기에 대한 검증반의 권한 확인 절차를 적용한다.
- DebugMCP는 사용자 명시 요청 없이 사용하지 않는다.

## 1. 비교 계약 확인

검증 전에 다음 항목을 기록한다.

1. 이관 대상 ValueP ID와 변경 범위.
2. 기존 소비처의 조회, 필터링, 변환 로직.
3. `getValueP`에 전달하는 좌표와 테스트 컨텍스트.
4. 비교 결과의 형태, 빈 결과 처리, 값 비교 기준.
5. 허용된 동작 변경과 지휘관의 완료 기준.

`from`은 이관 전 소비처 로직의 결과다. `to`는 같은 좌표에서 `getValueP`로 구한 결과다.

- 양쪽에 같은 좌표와 필요한 컨텍스트를 사용한다.
- `from`을 이관 후 `getValueP` 결과에서 만들지 않는다. 같은 구현을 두 번 호출한 비교는 이관 동등성을 입증하지 못한다.
- 기존 코드가 제거되었다면 이관 전 소스, 추적 가능한 스냅샷, 비교용 fixture 등 독립적인 기준을 확인한다.
- `undefined`, `null`, 빈 객체의 구분은 소비처 계약을 확인한다. 근거 없이 모두 빈 객체로 바꾸어 차이를 숨기지 않는다.
- 의도적인 결과 차이는 승인된 변경과 연결해 별도로 보고한다. 승인 없이 기대값을 새 결과에 맞추지 않는다.

## 2. 전체 좌표 수집 검토

필요한 좌표와 수집 원천은 ValueP ID에 따라 다르다. 아래 원천을 모두 사용하는 것이 필수는 아니다. 대상 소비처가 사용하는 좌표를 빠짐없이 포함해야 한다.

| 원천 | 확인할 좌표와 용도 |
| --- | --- |
| `ModuleManager` manifest, `BizzModuleIndex` | 업무 정의에서 `bizz_type`, `bizz_id`, `bizz_sid` 수집 |
| `us_menu_m`, 국가별 `us_menu_m_*` | 실제 메뉴의 `bizz_sid`, `menu_sid`, `menu_type` 수집 |
| `P_LOCATOR_MAP`의 PMS 항목 | `bizz_type` 또는 `bizz_id`와 `action_mode` 수집 |

### PMS 좌표

- `P_LOCATOR_MAP`에서 PMS 항목을 추리는 조건을 확인한다.
- locator 앞 값이 `EN_BIZZ_TYPE`에 포함되면 `bizz_type`으로 해석한다.
- 앞 값이 `bizz_id`이면 `BizzModuleIndex` 등 현재 업무 정의에서 `bizz_type`을 구한다.
- locator 형식과 모듈명 해석은 현재 코드에서 확인한다. 게시글의 문자열 분리 예시를 모든 locator에 적용하지 않는다.

### 실제 메뉴 좌표

- 대상 국가의 `us_menu_m*` 파일과 업무별 실제 메뉴를 확인한다.
- 같은 행의 `bizz_sid`, `menu_sid`, `menu_type`을 함께 사용한다.
- 게시글 예시는 누락된 `menu_sid`, `menu_sid === '*'`, 누락된 `menu_type`을 실제 메뉴 좌표에서 제외한다.
- 제외 조건이 현재 대상에도 유효한지 확인한다. 실제 메뉴의 `'*'` 제외와 ValueP wildcard 동작의 검증 제외를 혼동하지 않는다.

### 수집의 완전성

- 수집 원천, 읽은 파일 범위, 원천 좌표 수, 중복 제거 후 좌표 수를 기록한다.
- 중복 제거 키는 실제 사용한 좌표 필드를 기준으로 확인한다. 서로 다른 업무, 메뉴, action mode를 합치지 않는다.
- 제외한 좌표의 수와 사유를 기록한다. 업무 유형 조회 실패나 잘못된 locator를 조용히 버리지 않는다.
- 이관 전후 원천의 차이로 누락될 수 있는 좌표가 있는지 확인한다.
- '전수'는 수집한 전체 좌표 기준이다. 수집 범위 자체를 확인하지 못했다면 모든 업무를 검증했다고 보고하지 않는다.
- 좌표 0건, 일부 좌표만 실행, 이유 없는 제외는 전수 검증 통과가 아니다.

## 3. 개수와 내부 값 비교

전체 좌표마다 두 종류의 비교가 있는지 확인한다.

| 검증 | 확인할 차이 |
| --- | --- |
| 이관 전후 항목 개수 | 항목 추가 또는 누락 |
| 이관 전후 결과 내용 | key의 추가 또는 누락, 프로그램 ID 등 내부 값 차이 |

- 개수가 같아도 key나 내부 값은 다를 수 있다. 개수 비교만으로 통과를 선언하지 않는다.
- 게시글에 따르면 `Assert.equal`은 객체 내부 값까지 비교한다. 현재 `@test`와 기존 테스트의 동작을 확인해 사용한다.
- 객체 전체 비교로 추가와 누락을 양방향 확인한다. 한쪽 key만 순회하는 비교로 대체하지 않는다.
- 개수 비교와 내용 비교는 각각 해당 소비처의 의미를 보존해야 한다. 실행 항목만 비교하는 경우 기존 resolver 필터 등 변환 조건을 확인한다.
- 순서가 계약에 포함되면 순서를 보존한다. 정렬이나 필드 제거로 실제 차이를 숨기지 않는다.
- 실패 결과에는 ValueP ID, 좌표, `from`, `to`, 개수 차이 또는 값 차이를 연결한다.

검토할 의사 코드:

```text
이관 대상의 비교 계약을 확인한다.
원천에서 전체 좌표를 수집한다.
중복과 제외 사유를 확인한다.
각 좌표에 대해 반복한다.
    기존 소비처 로직으로 from을 구한다.
    같은 좌표와 컨텍스트로 getValueP를 호출해 to를 구한다.
    항목 개수를 비교한다.
    결과 전체의 key와 내부 값을 비교한다.
    좌표와 비교 결과를 기록한다.
수집한 좌표 수와 실제 비교한 좌표 수를 대조한다.
```

## 4. 상속, wildcard, clear 영향

ValueP는 상위 key의 설정을 하위 key가 상속한다. 변경한 상위 좌표만 확인하지 않는다.

- 상위 설정 변경으로 값이 바뀔 수 있는 하위 좌표를 포함한다.
- wildcard 설정을 적용받는 구체적인 하위 좌표의 결과를 확인한다.
- 하위 `clear` 규칙으로 상속을 차단하는 예외 좌표의 결과를 확인한다.
- 의도하지 않은 상속과 의도한 상속의 차단을 모두 확인한다.
- 해당 규칙이 대상 ValueP에 존재하지 않으면 근거와 함께 적용 대상 아님으로 기록한다. 관련 없는 규칙을 새 요구사항으로 만들지 않는다.

## 5. serial 보정과 비교용 fixture

### serial 보정

게시글 당시 `basic_code.serial`과 `inventory.serial`은 같은 `bizz_id`를 사용했다. `BizzModuleIndex`에는 먼저 등록된 모듈만 남았다. 당시 테스트 대상은 `inventory.serial`이었다.

- 같은 충돌이 현재도 존재하고 테스트 대상이 `inventory.serial`인지 확인한다.
- 조건이 맞는 경우에만 `basic_code` 조회 결과를 `inventory`로 보정한 케이스를 검토한다.
- 모든 `serial` 테스트에 무조건 적용하지 않는다.
- 보정 이유와 적용 좌표를 기록한다. 업무 ID가 유니크해졌다면 보정 제거를 개발반에 요청한다.

### 비교용 fixture

- 비교에는 가급적 실제 5.6 원천 데이터를 사용한다.
- 구조 차이 등으로 직접 비교하기 어려운 경우에만 비교용 복사본과 수정본을 사용한다.
- 비교용 fixture의 원천, 기준 리비전, 복사 이유, 수정 내역, 이관 전 의미의 보존 여부를 확인한다.
- 현재 `to`를 복사하여 기대값으로 사용하는 fixture는 독립적인 이관 전 기준이 아니다.
- 비교용 fixture 파일과 러너의 DB fixture 모드는 서로 다른 개념이다. DB fixture의 적용 여부는 기본 검증 절차로 별도 확인한다.

## 6. 실행과 판정

- 기존 서버 `*.spec.ts`를 Velox 테스트 환경에서 실행한다. Node 모의 구현이나 정적 검토만으로 서버 검증을 대체하지 않는다.
- 관련 파일부터 실행할 수 있지만, 최종 전수 검증은 수집한 전체 좌표가 실제로 비교되었을 때만 인정한다.
- 종료 코드, 이번 실행의 결과 JSON과 HTML 리포트, 실패 로그, 실행 및 skip 수를 확인한다.
- DB 확인이 필요한 항목은 실제 DB 검증 여부를 확인한다. `dry-run`이나 `off`를 실제 DB 검증 통과로 보고하지 않는다.
- 화면 확인이 완료 기준에 포함되면 지휘관에게 현장 조사반의 확인을 요청한다.
- 전수 테스트 통과와 실제 화면 확인 결과는 별도로 보고한다. 게시글의 '추가 오류 없음'은 당시 확인한 화면 범위에 한정된 사례다.
- 환경이나 권한 때문에 실행하지 못한 항목은 미검증으로 남긴다. 근거 없이 실패 원인을 단정하지 않는다.

## 결과 보고

기본 검증반 보고에 다음 항목을 추가한다.

1. 대상 ValueP ID, 변경 파일, 이관 전 비교 기준과 리비전.
2. 좌표 수집 원천, 원천 및 중복 제거 후 좌표 수, 제외 수와 사유.
3. 실제 비교 좌표 수, 성공, 실패, skip, 미검증 수. 테스트 함수 수와 좌표 수를 혼동하지 않는다.
4. 좌표별 개수 비교 및 내용 비교 결과. 실패한 좌표와 재현 입력.
5. 상속, wildcard, clear의 적용 범위와 검증 결과.
6. serial 보정과 비교용 fixture의 적용 여부 및 근거.
7. 수행한 명령, 실행 환경, 실제 DB fixture 모드, 리포트와 전체 로그 경로.
8. 실제 화면에서 확인한 업무, 메뉴, 동작과 결과. 미실행이면 미검증으로 표시한다.
9. 개발반에 요청할 테스트 보완이나 수정, 남은 검증 공백과 다음 확인 방법.

# Pi 시간로그 입력

요청한 한국 날짜에 실제 대화·작업한 Pi 세션들을 찾아 시간로그 초안을 만든다.
세션과 업무 정보 수집은 로컬 파일을 읽는다. 비고 작성은 Pi에 등록된 `openai-codex/gpt-6-luna`를 `low`로 호출한다.
로컬 초안 생성과 `/time-log preview`는 ERP API를 호출하지 않는다.
기존 날짜 명령과 submit 명령은 저장 확인창을 열기 전에 서버에서 기존 게시글을 조회한다.
게시글이 없으면 신규 작성하고, 있으면 그 글을 수정한다. 사용자가 확인창에서 승인한 경우에만 실제 저장한다.

## 설치

ContextGraph를 먼저 설치하고 `time-log` 폴더를 `<프로젝트>/.pi/extensions/time-log`에 추가한다.
공통 Pi SDK·TypeScript·Node 타입은 `.pi/package.json`에서 관리한다. 프로젝트 폴더의 PowerShell에서 공통 패키지를 먼저 설치한 뒤, 이 확장의 `puppeteer-core`를 설치한다.

```powershell
npm ci --prefix .\.pi
npm ci --prefix .\.pi\extensions\time-log
```

Pi의 디렉터리 확장 탐색은 `index.ts`를 읽는다.
별도 경로 등록 시 `.pi/settings.json`의 extensions에 `./extensions/time-log/index.ts`를 지정한다.

ContextGraph 소스나 공용 util을 import하지 않는다. 저장된 `.context` JSON과
`.pi/.local/context-connections`, Chrome registry의 JSON 계약으로만 연결된다.
전송 시 `puppeteer-core`가 저장된 로컬 WebSocket에 연결하고, 저장된 targetId의 탭만 사용한다.
Chrome 생성, 기본 브라우저 탐색, registry 변경은 수행하지 않는다.

## 사용법

`settings.json`에 확장과 `time_log_draft` 도구를 등록했다. 실행 중인 Pi에서 `/reload`로 반영한다.
현재 프로젝트의 저장 세션에서 ContextGraph 작업·거래 정보를 확인할 수 있어야 한다.
명령을 실행하는 세션 자체에는 업무 맥락이 없어도 된다.

```text
/time-log 2026-10-14
```

`/time-log ` 뒤에 이번 달 1일부터 한국 날짜 기준 오늘까지의 날짜를 자동완성으로 표시한다.
순서는 오늘부터 역순이며, 일부 날짜를 입력하면 해당 접두어와 일치하는 날짜만 표시한다.
예를 들어 오늘이 2026-10-15이면 2026-10-15, 2026-10-14, ... , 2026-10-01 순서다.
날짜 목록은 자동완성을 요청할 때마다 갱신하므로 날짜나 월이 바뀌어도 다시 로드할 필요가 없다.

이 명령은 해당 날짜의 업무 세션을 찾아 작업, 업무, 거래, 담당자, 부서, 일자와 비고를 채운다.
한 세션에서 업무 맥락이 바뀌었다면 각 실제 작업 기록에 적용돼 있던 맥락을 사용한다.
프로젝트·작업·거래가 같은 기록은 한 행으로 묶고 원본 세션 출처를 모두 표시한다.
비고는 모델이 같은 오류 맥락의 사용자·assistant 대화를 읽고 직접 작성한다.
날짜는 대상 세션을 고르는 기준이며, 비고의 근거에는 같은 문제의 이전 요청과 최종 결론도 포함한다.
처음 맥락을 연결하기 전의 사용자 요청도 첫 업무 맥락의 배경 자료로 함께 전달한다.
대화가 종결되었다고 가정하고, 해당 오류를 해결하면서 확정된 원인·수정·동작·결과를 중심으로 작성한다.
첫 항목은 해결하려던 구체적인 문제를 확인한 내용이다. 나머지는 확정 사실 최대 2개다.
`- `로 시작하는 최대 3개 항목으로, 하철환이 직접 작성한 것처럼 주어와 보고 표현을 생략한다.
"아님", "미확인", 추정, 미검증과 후속 계획은 최종 비고에서 제외한다.
부정문을 긍정문으로 바꾸지 않고, 해결 완료의 근거가 없으면 완료를 꾸며 쓰지 않는다.
확정 결과가 없다면 모델이 작성한 문제 확인 내용만 사용한다.
기존의 정규식 결과 추출·문체 치환·거래 제목 대체 요약은 제거했다.
초안의 카테고리는 개발로 고정한다.
초안의 시간은 비워 둔다. 일자, 작성일(전표 일자), 종료 예정일은 모두 명령에 지정한 날짜다.
예를 들어 `/time-log 2026-10-13`이면 작성일과 모든 상세 행의 종료 예정일도 `2026-10-13`이다.
기존 게시글의 같은 작업 행에 사람이 지정한 시간·카테고리·일자는 수정 저장할 때 보존한다.
프로젝트 코드는 작업을 식별하는 근거와 미리보기에 사용한다. 거래 SID로 대체하지 않는다.

프리뷰는 실제 화면의 작업명, PL명, 업무명, 거래명, 카테고리명, 시간(분), 시간, 종료 예정일, 비고 순서의 표다.
PL명은 작업의 지정된 PL 연결에서 확인한 경우만 표시하고, 없거나 충돌하면 빈칸이다.
모든 행, 원본 세션과 연결 정보를 확인하지 못한 세션의 제외 사유를 표시한다.
해당 날짜에 작업한 기록이 없는 세션은 제외 개수로 요약한다.
확인창은 신규 작성 또는 기존 게시글 수정 여부와 수정 대상 번호·제목을 함께 표시한다.
승인하면 프리뷰의 모든 행을 신규 시간로그에 저장하거나 기존 게시글에 병합한다.
Pi 터미널의 확인창도 표를 표시한다. Enter는 저장, Esc는 취소다.
방향키와 PageUp/PageDown, Home/End로 긴 표를 읽을 수 있다.
RPC 환경은 같은 항목과 비고를 일반 텍스트 확인창으로 표시한다.
취소하면 저장 API 요청을 보내지 않고 로컬 초안을 남긴다. 확인창 전에 실행한 읽기 전용 조회는 취소와 관계없이 이미 수행된 상태다.
대상 행이 없으면 확인창과 저장 요청을 실행하지 않는다.

취소한 초안은 다시 볼 수 있다.

```text
/time-log preview
/time-log submit <초안ID>
```

자연어로 `time_log_draft` 도구에 일별 프리뷰만 요청할 수도 있다.
이 도구는 비고 요약 모델을 호출한다. ERP 요청과 저장 확인창은 실행하지 않는다.

```text
2026-10-14에 작업한 세션들로 시간로그 프리뷰를 만들어줘.
```

도구는 초안 ID, 미리보기, 로컬 요청 본문 경로와 저장 명령을 반환한다.
도구로 준비한 초안을 저장하려면 다음 명령을 실행하고 확인창에서 승인한다.

```text
/time-log submit <초안ID>
```

날짜 명령과 submit 명령은 승인 후 **실제 저장 API를 호출한다**. 테스트 용도로 실행하지 않는다.
저장 후 시간은 ERP에서 사람이 지정한다. 종료 예정일이 다르면 ERP에서 수정할 수 있다.
저장 응답이 확인되면 게시글 번호와 거래 SID를 표시한다.
서버 응답을 실패로 판정하면 HTTP·ERP 상태와 확인 가능한 서버 오류를 표시한다.
자격 증명을 제거하고 크기를 제한한 응답 진단은 초안 옆의 `<초안ID>.response.json`에 저장한다.
신규·수정 각각의 성공 응답을 검증한 뒤 저장 완료로 처리하며, 실패 응답을 자동 재전송하지 않는다.

## 기존 게시글 조회와 수정

새 command는 추가하지 않는다. `/time-log YYYY-MM-DD`와 `/time-log submit <초안ID>` 안에서 다음 순서로 처리한다.

1. 로컬 초안을 만들거나 읽고 원본 세션을 검증한다.
2. ContextGraph에 연결한 ERP 탭에서 현재 조회 메뉴·양식과 시간로그 목록을 읽는다. 기존 글이 있으면 해당 글의 입력 모델도 읽는다.
3. 신규 또는 수정 계획과 업무 프리뷰를 확인창에 표시한다.
4. 승인 후 같은 날짜 범위의 저장 잠금을 잡고 서버 상태를 다시 조회한다. 검토했던 계획·대상·본문과 같은지 확인한다.
5. 신규는 CreateBoardAction, 수정은 ModifyBoardAction으로 한 번 저장한다.

대상 글은 회사, 현재 로그인한 작성자, 설정된 담당자, 업무일자가 모두 정확히 일치해야 한다.
최상위 정상 게시글만 대상으로 하며 제목 문자열이나 로컬 저장 응답으로 기존 글을 추정하지 않는다.
동일 조건의 글이 여러 개이거나 조회·불러오기·응답 검증이 실패하면 중단한다. 조회 실패를 글 없음으로 취급해 신규 작성하지 않는다.
저장 응답의 로컬 기록은 결과 확인용이며, 서버의 게시글 존재 여부를 대신하지 않는다.

사이트에서 수정한 내용은 저장 전에 읽은 최신 게시글을 기준으로 처리한다. 사이트에서 편집하지 말아야 한다는 제약은 없다.
확인창 전 조회 시점에 기존 글이 삭제되어 없으면 신규 작성으로 안내한다.
조회 이후 확인 대기 중이나 저장 직전에 글이 삭제·수정되거나 새 글이 생기면 저장을 중단한다.
수정 승인을 받은 뒤 신규 작성으로 바꾸거나, 신규 승인을 받은 뒤 기존 글을 덮어쓰지 않는다. 다시 수동 저장하면 최신 상태로 계획을 다시 확인한다.

수정 시에는 기존 상세 행의 작업·업무·거래 연결 SID 조합을 초안의 행과 대조한다.
연결이 같은 행은 비고만 이번 초안의 요약으로 교체하고 시간·카테고리·일자·레코드 식별자 등 나머지 값을 유지한다.
초안에 없는 연결의 기존 행과 연결 없이 사람이 추가한 행은 그대로 두며, 새 연결의 행은 상세 끝에 추가한다.
같은 작업·업무·거래 연결의 상세 행이 여러 개라면 자동 병합을 중단한다.
기존 제목·마스터 값·에디터 본문도 보존한다. 기존 행의 순서는 유지한다.
서버 수정은 전달받은 전체 상세 행을 기준으로 저장하므로, 기존 행을 제외한 새 행만 보내지 않고 보존할 행까지 함께 전송한다.

따라서 재실행은 같은 날의 글을 다시 만들지 않고 최신 글에 비고와 새 업무 행을 반영한다.
새 초안에 나오지 않은 기존 행을 자동 삭제하는 방식은 아니다.

## 조사한 입력 계약

첨부한 요청, JSON 본문, 성공 응답, 화면을 기준으로 구성했다.
상단 일자, 전표 일자, 상세 종료 예정일은 서로 다른 필드다. 신규 초안에서는 모두 요청한 날짜로 채운다.

```text
시간로그 업무: B_000000E074025
입력 메뉴: M_000000E074025
양식: 7VC6DMBMUFD7GKP
카테고리: 13 / 개발

작업: board_m$conn_data_002
업무: board_m$dynamic_bizz
거래: board_m$dynamic_trx
일자: board_s$dt_001
전표 일자: board_s$data_dt 및 slip_info.data_dt
종료 예정일: board_m$dt_001
시간: board_m$num_001
총시간: board_s$num_001
비고: board_m$atxt_001
```

첨부 두 번째 상세 행은 작업과 테스트오류수정 거래가 서로 다르다.
구현은 상위 작업 연결과 현재 게시글의 업무·거래 연결을 별도로 채운다.
종료 예정일 매핑은 화면의 열 이름과 첨부 상세 날짜 필드에 근거한다.
별도 양식 설정을 조회해서 확인한 결과는 아니다.

시간을 생략하면 상세 시간은 `null`이다. 하나라도 시간이 비어 있으면 총시간도 `null`이다.
지정한 시간은 양의 정수이며, 모든 시간이 지정된 경우에만 합계를 계산한다.
일별 명령은 모든 행에 종료 예정일을 명시한다.
실패 응답에서 전달자와 8개 상세 일자의 `condition_not_null` 검증 오류를 확인했다.
전달자 범위는 첨부된 정상 입력과 같은 전체(A)를 기본값으로 사용하며, 미리보기에도 표시한다.
알림 채널은 계속 사용하지 않는다. 별도 전달 대상을 쓰려면 profile에 선택(S)과 실제 ERP 사용자 코드를 명시한다.

CreateBoardAction과 SlipDefaultValueAttrProgram 소스는 신규 저장 시 서버가 전표·레코드 SID를 생성함을 보여준다.
첨부 응답도 요청의 이전 상세 레코드 SID를 새 SID로 대체한다.
신규 payload는 이전 전표, 작성자·수정자, 중첩된 원본 레코드와 알림 수신자를 복사하지 않는다.
알림 채널은 모두 사용하지 않는 상태로 생성한다. 수정 payload는 서버에서 읽은 기존 전표와 행 식별자를 사용한다.

### 5.0 신규 입력 모델과 대조한 보완

5.0의 `CreateAndModifyBoardUserAction` → `ExecuteSetupMainProgram.getActionRequest`는
입력 DMC를 직렬화해서 보낸다. 원본에 있던 필드를 업무 값만 추려서 구성하면서 생략한 차이를
5.0 입력 모델, 자료형 기본값 생성기, 신규 저장 기본값 Feature 및 5.6 저장 초기화와 대조했다.

원본에서 빠진 최상위 키 42종 중 마스터 16종·상세 3종·에디터 5종을 복원했다.
필드가 원본에 있다는 사실만으로 서버가 필수로 요구한다고 판단하지는 않는다.
서버가 다시 채우는 필드도 입력 모델과 같은 기본값을 보내도록 보완한 것이다.

```text
마스터: record_sid="", record_depth_no/record_seq_no/ver_no/reply_cnt=0,
        status_type="U", repo_sid="R_000000E074025", data_model_id="board_master",
        bizz_class_sid="BC_00000E074025", hid=null,
        slip_link={slip_attach:{}, file_attach:{}}, action_mode="",
        cust_sid/pjt_sid/prod_sid/dynamic_bizz_sid=""
상세:   record_sid=행마다 다른 임시 SID, status_type="", item_set_sid=""
에디터: editor_sid=새 임시 SID, record_sid="", status_type="U",
        item_set_sid/item_sid=""
```

임시 SID는 ERP의 최종 식별자가 아니다. 원본의 15자리 표현에 맞는 로컬 키를 만들고,
신규 저장 시 서버가 최종 키로 대체한다. 같은 검토 내용을 재구성할 때는 같은 키가 나온다.
키를 만들기 위한 조회/채번 API는 호출하지 않는다.
전표 SID·번호와 마스터/에디터 레코드 SID는 신규 입력의 빈 상태로 둔다.
항목 집합과 에디터 항목 SID는 기존 문서에서 복사하지 않고 서버의 현재 업무 설정에 맡긴다.

나머지 18종은 인증 사용자에서 생성되는 작성자/수정자 값 또는 참조 확장 캐시다.
원본에 있던 문자 그대로의 `undefined` 키도 복사하지 않는다.
알림 수신자와 기존 보류 SID는 신규 입력에 추가하지 않는다.
신규 payload의 상세 분류·일자·비고·연결 필드는 현재 세션 자료와 지정한 날짜를 사용하며 시간은 공란이다.

신규 필드 구성은 `src/erp/payload.ts`, 기존 글 조회와 병합은 `src/erp/upsert.ts`를 기준으로 한다.

## 세션 정보 복원

현재 Pi 세션 디렉터리 바로 아래의 JSONL 파일과 현재 세션의 메모리 기록을 읽는다.
다른 프로젝트와 하위 서브에이전트 세션은 포함하지 않는다.
생성일, 수정일, 파일 mtime 대신 메시지 항목의 실제 기록 시각을 한국 날짜로 판정한다.
다른 branch에서 실제 수행한 작업도 해당 메시지의 상위 연결을 따라 당시 맥락으로 집계한다.
fork에 복사된 기존 메시지는 새로운 작업으로 중복 계산하지 않는다.
현재 세션의 아직 파일에 기록되지 않은 내용도 포함한다. 다른 프로세스의 미저장 내용은 볼 수 없다.

각 작업 기록에 적용돼 있던 `ec-context-session` 선택을 읽는다.
저장된 catalog, entry, post JSON과 완료된 수집 파일을 검사한다.
수집 파일의 업무 SID와 거래 SID를 게시글 종류·번호 및 연결 작업과 대조한다.
파일 변경, 서로 다른 거래 SID, 잘못된 작업 연결은 거부한다.
표시 번호나 프로젝트 코드로 거래 SID를 추정하지 않는다.

`--only` 수집에서 상위 작업이 빠졌다면 자동으로 수집 범위를 넓히지 않는다.
세션에 저장된 jobKey를 명시적인 연결 정보로 사용해 로컬의 작업 식별값을 확인한다.
세션의 jobKey가 null이면 당시 작업이 미확정이었던 기록으로 취급한다.
이후 로컬 그래프 메타데이터에서 연결 작업이 확인되면 해당 작업의 저장 파일과 완료 캡처를 대조한다.
이를 통해 시간로그의 작업 식별값만 읽으며, `--only` 그래프와 원본 세션은 변경하지 않는다.
이때도 알려진 작업 관계와 다른 작업은 거부한다.
완료된 로컬 캡처가 없으면 초안을 만들지 않는다. 원격 조회로 보충하지 않는다.

실제 저장 파일로 `2026-10-14`를 검사했고 3개 세션에서 3개 행을 구성했다.
연결은 `job:11218`의 `tp:28450`, `tp:28491`, `tp:28502`였다.
작업 거래와 TP 거래는 서로 다른 필드에 들어갔다.
초기 검사에서 시간과 종료 예정일은 빈값, 카테고리는 개발이었다.
실제 실패 응답과 사용자 날짜 지정에 따라 이후 초안은 작성일과 종료 예정일을 요청한 날짜로 채운다.
현재 작업이 없는 파일, 맥락이 없는 기록, 작업 연결이 없는 기록과 잘못된 세션 파일은 제외했다.

## 설정과 저장 제어

비고 모델은 현재 Pi의 모델 레지스트리와 인증을 사용한다. 기본값은 Luna low다.
`time-log.json`의 `remarksModel`로 provider/model을 지정할 수 있으며 추론 수준은 `low`를 사용한다.
모델이 없거나 호출·응답 검증에 실패하면 초안을 저장하지 않는다. 정적 요약으로 대체하지 않는다.
요약 도구의 schema에 한 줄·240자 제한과 이번 입력의 근거 ID를 명시한다.
최종 문제의 '확인' 표현은 지시문에 명시하고 모델 반환 후 검사한다.
형식·근거 검증에 실패하면 실패한 필드와 이유를 모델에 전달해 같은 원문으로 한 번만 다시 작성한다.
재작성도 검증을 통과해야 하며, 반복 실패 시 거래명·요약 단계·필드·이유를 표시하고 초안을 저장하지 않는다.
서로 다른 업무 행의 요약은 최대 3개씩 병렬 실행한다. 같은 작업·거래의 세션은 먼저 합쳐 한 업무로 요약한다.
각 업무 안의 분할 요약과 최종 통합은 순서대로 실행하므로 전체 모델 호출도 동시에 최대 3개다.
완료 순서와 관계없이 프리뷰, 요청 행과 근거 기록은 원래 업무 순서를 유지한다. 진행률은 완료 건수다.
한 업무가 실패하면 새 업무를 시작하지 않고 나머지 호출을 취소한다. 실행 중 호출이 정리될 때까지 기다린 후 실패를 반환한다.
요약 진행은 상태줄에 표시하며 도구 취소·세션 종료 시 모델 호출을 취소한다.
긴 대화는 분할 요약 후 통합한다. 철회·정정 정보는 중간 요약에 보존해 최종 확정 사실 선정에 사용한다.
각 최종 항목의 원문 메시지 ID와 모델·정책·호출 횟수는 초안에 기록한다.
대화 원문은 ERP 본문과 초안에 넣지 않으며, 인증 정보는 모델 입력에서 가린다.
모델 입력에 사용한 이전/최종 대화가 수정되거나 삭제되면 초안을 무효화하고 다시 작성하게 한다.
수집 이후 추가된 대화와 작업은 기존 초안에 포함하지 않고 다음 날짜 명령에서 반영한다.

기본 회사, 부서와 담당자는 첨부에서 관측한 `80000`, `5.6TFT`, `2025-053 / 하철환`이다.
접속 대상은 현재 Pi 세션에서 ContextGraph가 연결한 탭이다. 별도의 호스트를 선택하지 않는다.
필요하면 `.pi/time-log.json`에 `contextDir`, `profile`을 지정한다. 이전 `host` 설정은 사용하지 않는다.

```json
{
  "remarksModel": { "provider": "openai-codex", "model": "gpt-6-luna" },
  "profile": {
    "tenantSid": "80000",
    "templateSid": "7VC6DMBMUFD7GKP",
    "department": { "sid": "5.6TFT", "code": "5.6TFT", "name": "5.6TFT" },
    "person": { "sid": "2025-053", "code": "2025-053", "name": "하철환" },
    "deliver": { "type": "A" }
  }
}
```

전송은 ContextGraph와 같은 Chrome 브라우저와 저장된 탭 고유 ID를 사용한다.
페이지 번호가 바뀌어도 새로 찾은 번호와 고유 ID를 대조해 같은 탭을 선택한다.
ContextGraph에 연결된 5.0 또는 5.6 ERP 화면의 현재 호스트에서 시간로그의 5.6 API를 호출한다.
탭이 닫혔거나 연결이 바뀌면 다른 탭으로 대체하지 않고 중단한다.
기존 연결은 저장된 탭이 하나인 경우 그대로 사용한다. 여러 기존 연결이 모호하거나 연결이 없으면 `/ec-connect`로 사용할 탭을 정한다.
브라우저 생성, 로그인과 페이지 이동은 실행하지 않는다. 저장 계획을 만들고 재검증하기 위한 양식·목록·입력 모델 조회 API는 실행한다.
현재 URL의 세션과 현재 회사가 일치해야 한다.
알려진 로그인 사용자가 바뀌거나 사라지면 전송을 중단한다.
인증 쿠키와 세션 SID는 브라우저에서만 사용한다. 첨부의 인증값을 재사용하거나 저장하지 않는다.
현재 버전 헤더는 ERP의 기존 헤더 함수를 사용한다. 기록된 버전 번호는 복사하지 않는다.

초안과 전송 상태는 `.pi/.local/time-log/`에 저장한다.
확인 요약, 요청 본문, 대상과 세션 연결 정보가 변경되면 저장을 거부한다.
명령을 실행한 소유 세션이 변경되거나 다른 세션의 초안을 재사용하면 거부한다.
현재 선택 맥락만 바뀌는 것은 일별 초안을 무효화하지 않는다.
수집에 포함된 실제 작업 기록, 당시 연결 맥락이나 로컬 거래 식별 정보가 변경되면 저장을 거부한다.
시간로그 자체의 초안·프리뷰 기록은 원본 변경으로 처리하지 않는다.
각 원본의 수집 경계(항목 수·마지막 항목 ID)를 초안에 저장하고, 그 경계까지의 근거를 재검증한다.
경계 뒤에 새 대화·도구 실행·맥락 선택이 추가돼도 기존 초안의 근거가 유지되면 저장할 수 있다.
수집에 포함된 대화를 대상으로 한 후속 context_edit는 계속 변경으로 판단한다.
경계 정보가 없는 기존 초안은 이전의 엄격한 전체 원본 검사를 유지한다. 날짜 명령으로 다시 생성하면 새 기준을 적용한다.
프리뷰는 수집 시점의 집계다. 이후 추가된 작업이나 새 세션을 포함하려면 날짜 명령을 다시 실행한다.
한 번 저장을 시도한 초안은 다시 전송하지 않는다. 후속 반영은 날짜 명령으로 새 초안을 만든다.
회사·로그인 작성자·담당자·업무일자가 같은 저장은 `.pi/.local/time-log/.claims/`의 공통 잠금으로 다른 Pi 세션과도 경합을 막는다.
잠금은 승인 후에 잡으며, 성공 응답을 로컬에 기록한 뒤 해제한다. 실제 저장 요청을 보내지 않았음이 확인된 실패에서도 해제한다.
전송 결과가 불명확하면 잠금을 유지한다. 이 경우 새 Pi 세션이나 새 초안으로 같은 날짜 저장을 우회하지 못한다.

전송이 시작되지 않았다고 확인된 실패는 같은 초안을 다시 수동 저장할 수 있다.
필수값·날짜·입력 메타데이터 기준을 변경하기 전에 생성한 초안은 저장할 수 없다.
현재 입력 정책 버전은 4이며, 이전 초안은 날짜 명령으로 새 미리보기를 생성해야 한다.
전송 후 타임아웃, 연결 끊김, 해석할 수 없는 응답은 `uncertain`으로 기록한다.
이 경우 자동 재전송하지 않는다. 새 초안을 만들기 전에 ERP에서 실제 저장 여부를 확인한다.
응답 진단 파일에는 실패한 판정 항목, 응답 구조와 서버 오류가 남는다.
원문 본문, 요청 쿠키, 로그인 SID와 스택은 기록하지 않는다.
이 진단 기록을 추가하기 전에 실패한 요청의 응답은 기존 초안 파일에서 복원할 수 없다.

## 오프라인 검증

다음 명령은 실제 네트워크와 하위 프로세스 실행을 차단한다.
브라우저는 주입한 모의 객체만 사용하고, 생성한 전송 스크립트는 격리된 VM의 모의 fetch로 검사한다.

설치 절차를 마친 뒤 프로젝트 폴더의 PowerShell에서 실행한다.

```powershell
npm test --prefix .\.pi\extensions\time-log
npm run check --prefix .\.pi\extensions\time-log
```

오프라인 테스트와 TypeScript 검사로 날짜 필터, 원본 연결, 프리뷰 승인과 모의 전송을 검사한다.
설치된 Pi의 실제 확장 로더도 네트워크 없이 검사한다.
같은 연결 탭의 재사용, 표 렌더와 확인·취소, 비고 제한을 포함해 오프라인 검사한다.
신규/수정 라우팅은 서버 목록의 정확한 대상 판별, 중복·조회 오류 차단, 기존 행 병합과 수동값 보존을 검사한다.

이 검사의 모델·브라우저·ERP 응답은 모의다. 실제 ERP 저장 성공을 검증하지 않는다.
